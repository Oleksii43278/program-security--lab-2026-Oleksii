# Архітектурний опис TaleSpire GM Logger

## 1. Зацікавлені сторони та їхні інтереси
* **Game Master (GM):** Зацікавлений у стабільності роботи застосунку, швидкості створення записів під час гри та неможливості втрати даних через збій.
* **Гравці:** Зацікавлені у криптографічній гарантії того, що збережений лог не піддавався модифікації після завершення сесії.

## 2. Представлення системи (Views)

### 2.1. Компонентне представлення
Система є монолітним локальним скриптом (CLI-застосунком) на Python. Складається з трьох логічних модулів:
1. **Інтерфейс вводу (CLI):** Приймає команди від користувача.
2. **Ядро хешування:** Зчитує попередній хеш, формує новий блок даних, обчислює SHA-256.
3. **Модуль зберігання:** Відповідає за атомарний запис у локальний JSON-файл.

### 2.2. Представлення розгортання
Застосунок розгортається безпосередньо на комп'ютері Game Master-а. Не потребує сервера, бази даних чи підключення до Інтернету. Усі артефакти знаходяться в одній директорії операційної системи.

## 3. Архітектурні рішення (AD)

**AD-01: Зберігання логу у форматі JSON (Append-only)**
* **Контекст:** Необхідно обрати формат для зберігання локального логу.
* **Альтернативи:** СУБД SQLite, бінарний формат, звичайний TXT.
* **Рішення:** Обрано JSON.
* **Обґрунтування:** JSON є людиночитним, що дозволяє гравцям легко перевірити лог без спеціального ПЗ (вимога NFR-02). 
* **Наслідки:** Система повинна обробляти файл виключно дописуванням нових даних у кінець.

**AD-02: Ізоляція від процесу TaleSpire**
* **Контекст:** Як застосунок отримуватиме дані про події гри.
* **Альтернативи:** Читання оперативної пам'яті гри, хук мережевих пакетів, ручне введення GM-ом.
* **Рішення:** Виключно ручне введення подій через консоль застосунку.
* **Обґрунтування:** Читання пам'яті може сприйматися античит-системами як втручання. Ручне введення дозволяє фіксувати не лише системні кидки, а й сюжетні рішення.
