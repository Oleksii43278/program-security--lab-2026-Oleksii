# Модель керування доступом — TaleSpire GM Logger

## 1. Обрана модель
Для інструмента `drs_release` обрано змішану модель керування доступом (RBAC + ABAC + DAC), оскільки жодна окрема модель не покриває всі вимоги безпеки. Мандатна модель (MAC) не застосовується, оскільки в системі немає даних різних рівнів секретності.

## 2. Суб'єкти, ресурси та атрибути
* **Суб'єкти:** Автентифіковані користувачі (Game Masters / супроводжувачі).
* **Ролі (RBAC):** `viewer` (перегляд), `maintainer` (базове адміністрування), `owner` (повний контроль). Ролі успадковуються: `owner` має всі права `maintainer`, а той — усі права `viewer`.
* **Атрибути контексту (ABAC):** Час останнього введення пароля (Step-up автентифікація). Критичні операції вимагають свіжого підтвердження (не старше 5 хвилин).
* **Власність (DAC):** Належність облікового запису конкретному користувачу (впливає на право зміни пароля).

## 3. Правила доступу
| Операція | Мінімальна роль (RBAC) | Додаткові умови (ABAC / DAC) |
| :--- | :--- | :--- |
| `list-users`, `status` | `viewer` | — |
| `passwd` | — (DAC) | Зміна власного пароля АБО наявність ролі `owner`. Потребує Step-up. |
| `add-user`, `set-role` | `owner` | Потребує Step-up. Неможливо зняти роль `owner` з останнього власника. |

## 4. Примусове забезпечення (Enforcement)
Перевірка прав виконується централізовано через модуль `authz.py` (функція `authorize`) безпосередньо перед виконанням захищеної операції (SR-24). Відмова користувачу є загальною ("Операцію відхилено"), а точна причина фіксується виключно в журналі аудиту (SR-26)[cite: 43, 45, 47].
